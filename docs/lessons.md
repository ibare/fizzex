## L1. baseline 비교 시각화 — input 공통 요소는 차별화하지 않는다

**Date**: 2026-04-16
**Source**: 케플러 PoC 첫 구현 후 사용자 피드백 ("궤도는 공통 요소인데 빨간색으로 변하니까 매우 혼란스럽다")

### 문제
초기 구현에서 `isStandard === false` 일 때 궤도 원까지 빨간 실선으로 바꿨음.
하지만 궤도 반지름은 input 파라미터 `a` 로만 결정되고, 식 구조 변형(T²의 지수, 4π², a³의 지수)은 **derived 값(T, v)에만** 영향을 준다.
baseline 과 current 모두 같은 `a` 를 받으므로 궤도 원은 항상 같은 위치 — 색상 구분이 시각적 노이즈를 만들었다.

### 패턴
**baseline 비교 시각화에서 차별화 대상은 derived 값에 의존하는 요소뿐이다.**

| 요소 | 의존 | baseline/current 차별화? |
|------|------|------------------------|
| 위치/크기 (input parameter 만) | input | ❌ 동일 — 차별화 의미 없음 |
| 회전 속도, 색조 등 (derived 값) | derived | ✅ 차별화 — 식 구조 효과 |
| 정량 비교 (텍스트) | derived | ✅ "표준 대비 X%" |

### 적용 체크리스트
새 카탈로그 시각화에 baseline 비교를 도입할 때:
1. 해당 요소가 input 만으로 결정되는가? → 색상/위치 차별화 금지
2. 해당 요소가 derived(또는 equationValue) 에 의존하는가? → 차별화 OK
3. 의심되면 "같은 input → baseline 과 current 가 같은 값을 그릴까?" 자문

## L2. replace_all 치환은 방금 추가한 getter 본체까지 삼킨다

**Date**: 2026-04-19
**Source**: Phase 1.4 kepler three-core-renderer isDark getter 도입 중 self-recursion 발생, rule-guard 사후 검증에서 적발

### 문제
1. `private get isDark(): boolean { return this.theme === 'dark'; }` getter 추가
2. 동일 파일에서 `Edit(replace_all: true, old: "this.theme === 'dark'", new: "this.isDark")` 실행
3. getter 본체의 `this.theme === 'dark'`까지 함께 치환되어 `return this.isDark` → 무한 재귀
4. `pnpm tsc --noEmit`은 통과 (타입은 여전히 boolean) — 런타임 크래시를 잡지 못함

### 패턴
**같은 파일에 "소비 지점"과 "원천 정의"가 공존할 때 replace_all 금지.**

- getter/상수/파생 함수 본체는 치환 대상 패턴을 **유일하게 남겨둬야 할 장소**다
- `Edit(replace_all)`은 소비자만 바꿔야 하므로, 원천을 먼저 다른 표현으로 분리(별도 변수, 또는 getter 추가 시점 분리)하거나, 개별 Edit으로 명시적 치환할 것
- 정말 replace_all이 필요하면 치환 직후 **해당 파일의 getter/상수 정의 라인을 직접 읽어 재귀 여부 확인**

### 적용 체크리스트
- [ ] 치환 패턴이 파일 내에서 "원천 정의 라인"에 등장하는가? → replace_all 금지
- [ ] replace_all 수행 후 getter/상수 정의 본체를 grep 또는 Read로 확인했는가?
- [ ] `tsc --noEmit` PASS만으로 치환 검증을 종결하지 말 것 — self-recursion은 타입 통과

## L3. 문서를 고칠 때 검증 없이 쓰면 같은 문제를 재생산한다

**Date**: 2026-09-05
**Source**: 시각화 문서 재편. rule-guard 6라운드에서 내가 낸 사실 오류 12건 적발

### 문제

낡은 문서를 정리하면서 "지금 무엇이 되는가"를 적었는데, 그 서술 자체가 여러 번
틀렸다. 원래 고치려던 문제(문서가 코드와 어긋남)를 새 문서에서 그대로 재생산했다.

대표 사례:

| 내가 쓴 것 | 실제 |
|---|---|
| `warnOnce` 라 "1회뿐이라 알아채기 어렵다" | 직전 키만 억제 — 두 곳이 번갈아 던지면 **매 프레임** 경고 |
| "프레임 전체가 스킵된다" | catch 가 셋. animation 만 프레임을 건너뛰고, render 는 그 지점 이후만 누락 |
| `viewports` 사용 8 / 빈 것 9 | **9 / 8** (뒤집힘) |
| "3·4단계 누락을 테스트가 잡는다" | 4단계(form 등재)는 잡지 않는다 |
| 카탈로그 로케일 파일에 `entries[]` | 항목 id 를 키로 하는 평평한 객체 |

### 패턴

**한 겹만 확인하고 결론을 적었다.**

- 이름에서 동작을 추정했다 (`warnOnce`, `evaluable`, `analyzePolynomial`)
- 경로가 여러 개인 곳을 하나로 뭉갰다 (catch 3개, fallback 분기)
- 숫자가 우연히 맞아떨어지자 검산을 멈췄다 (`8+9=17`)
- 소스 주석을 근거로 삼았다 — 그 주석 자체가 부채였다. `render-context.ts` 가
  존재한 적 없는 `theme` 필드를 문서화하고 있었다

### 적용 체크리스트

- [ ] 동작을 주장하기 전에 스크립트로 실행해 출력을 확인했는가?
- [ ] 문서에 적은 예시 코드를 **그대로 실행해** 대조했는가?
- [ ] 분기·catch·fallback 이 여러 개인 곳을 각각 확인했는가, 요약만 했는가?
- [ ] 소스 주석을 근거로 쓰지 않았는가? (주석도 검증 대상이다)
- [ ] 내가 다른 파일에 써둔 경고를 이 변경이 위반하지 않는가?

## L4. 서브에이전트의 보고는 근거가 아니라 검증 대상이다

**Date**: 2026-09-08
**Source**: `fizzex/compute` 서브패스 신설. 설계 검토 서브에이전트의 보고 4건 중 1건이 사실과 반대였고,
문서에 그대로 옮겼다가 실측에서 잡음

### 문제

설계 검토를 맡긴 에이전트가 "워커 경계 함정" 으로 두 가지를 보고했다.

| 보고 | 실측 |
|---|---|
| 노드 ID 가 파싱마다 리셋돼 수식 간 충돌 | **사실** — 두 수식이 7개 id 를 공유 |
| `evaluateSync('1/0')` 가 `Infinity` 를 내므로 JSON RPC 가 깨진다 | **반대** — `undefined` 를 내고 `evaluate` 는 `{ok:false, status:'divergent'}`. evaluator 가 비유한값을 애초에 걸러낸다 |

두 번째를 검증 없이 README 에 "results pass structuredClone but they are not JSON" 이라고
적었다. 소비자에게 존재하지도 않는 함정을 경고하는 문서가 될 뻔했다.

### 패턴

**신뢰도가 높은 보고일수록 통째로 통과시키게 된다.** 같은 에이전트의 다른 지적
(semantic JSON 524KB, `determineRenderMode` 가 이미 클로저 안, utils 는 id-generator 하나뿐)이
전부 실측으로 확인되자, 나머지도 확인 없이 받아들였다. 보고의 평균 정확도는 개별 항목의
보증이 아니다.

L3 이 "문서를 고칠 때 한 겹만 확인하고 결론을 적었다" 였다면, 이건 **아예 확인하지 않고
남의 결론을 옮긴** 경우다. 출처가 코드가 아니라 사람(또는 에이전트)이면 오히려 더 위험하다 —
근거를 확인했다는 착각이 붙기 때문이다.

### 적용 체크리스트

- [ ] 서브에이전트가 보고한 **동작**을 내 손으로 실행해 봤는가? (구조·경로 보고와 동작 보고는 다르다)
- [ ] 그 보고를 문서·주석·커밋 메시지에 옮기기 전에 실측했는가?
- [ ] 같은 보고서의 다른 항목이 맞았다는 이유로 이 항목을 건너뛰지 않았는가?
- [ ] 코드가 "정규화한다 / 걸러낸다" 고 주석에 써 둔 지점을, 반대로 주장하는 보고를 받았을 때
      양쪽 다 실행해 봤는가?

## L5. 검증 도구가 무엇을 못 보는지 먼저 확인한다

**Date**: 2026-09-08
**Source**: `fizzex/compute` 서브패스 신설. "루트 공개 표면 회귀 없음" 을 선언했는데
타입 export 26종이 실제로 사라져 있었고, rule-guard 사후 검증에서 BLOCKER 로 적발

### 문제

루트 배럴을 재편한 뒤 회귀가 없음을 이렇게 확인했다.

```js
// 변경 전 dist 와 변경 후 dist 의 export 키 비교
node -e "import('./dist/index.js').then(m => console.log(Object.keys(m).sort()))"
// → 사라진 심볼 0개, 11개 추가. "회귀 없음" 이라고 보고했다
```

`Object.keys` 는 **런타임 값만 본다.** 인터페이스와 타입 별칭은 컴파일 시점에 지워지므로
이 비교에 애초에 등장하지 않는다. `MathNode`, `RootNode` 를 비롯한 노드 타입 26종을
루트 재수출 목록에 옮겨 적지 않았는데도 검사는 초록불이었다.

`pnpm typecheck` 도 통과했다. `tsconfig.typecheck.json` 의 `include` 가 `src/**` 뿐이라
`fizzex` 를 소비하는 `website/` 를 보지 않기 때문이다. 실제로 `tsc -b website/tsconfig.json`
은 `TS2305: Module '"fizzex"' has no exported member 'RootNode'` 로 깨져 있었다.

즉 **두 검증이 다 초록이었는데 둘 다 이 회귀를 볼 수 없는 도구였다.**

### 패턴

검증을 실행한 것과 검증이 그 문제를 볼 수 있는 것은 별개다. 나는 도구를 돌렸다는 사실을
근거로 삼았지 그 도구의 사각지대를 확인하지 않았다.

- 런타임 리플렉션(`Object.keys`, `import()`)은 타입 표면을 못 본다 → `ts.createProgram` +
  `TypeChecker.getExportsOfModule` 로 봐야 한다
- 패키지 내부 `typecheck` 는 소비자 관점을 못 본다 → 실제 소비자(`website/`)나 tarball 을
  설치한 별도 디렉터리에서 확인해야 한다
- 정적 스캔은 `dist` 의 elide 된 import 를 못 본다 → src 를 스캔해야 한다

### 적용 체크리스트

- [ ] 이 검증이 **못 보는 것**이 무엇인지 한 문장으로 말할 수 있는가?
- [ ] 공개 표면을 건드렸다면 타입 export 까지 비교했는가? (`Object.keys` 로 끝내지 않았다)
- [ ] 패키지 밖 소비자(website, tarball 설치본)에서도 빌드해 봤는가?
- [ ] 새로 만든 회귀 테스트를 **일부러 깨뜨려** 실제로 실패하는지 확인했는가?

## L6. 진단이 맞아도 처방이 충분한지는 따로 물어야 한다

**Date**: 2026-09-09
**Source**: 호스트가 PDF 프린트 서버를 붙이려다 막혀 "`exports` 에 한 줄이면 된다,
서버는 한 글자도 안 고쳐도 된다" 는 해법을 제시. 진단은 정확했고 처방은 부족했다

### 문제

호스트의 진단은 옳았다 — `dist/browser/fizzex-export.js` 가 매 빌드마다 나오는데
`exports` 에 없어서 Node 캡슐화에 막힌 게 맞았다. `vite.lib.config.ts` 헤더가
"IIFE bundle for use in Playwright for print/PDF rendering" 이라고 목적까지 적어
두고 있었다.

그 한 줄을 뚫어도 렌더는 깨진다. 확인해 보니 구멍이 셋이었다.

| 확인한 것 | 결과 |
|---|---|
| tarball 안의 폰트 파일 | **0개** (`files` 에 `fonts/` 없음) |
| 번들이 참조하는 폰트 URL | `/fonts/...` 절대경로 하드코딩, 인라인 없음 |
| `setMathFontUrl` 이 번들 표면에 | **없음** (`src/export/index.ts` 가 png-renderer 만 재수출) |

`about:blank` 에 주입하는 호스트는 반드시 404 를 맞고 fallback 폰트로 조판된다.
"한 줄이면 끝" 이라는 판단은 호스트가 아직 번들 로드에 성공하지 못해 그 다음
구멍을 만나지 못했기 때문이었다.

### 패턴

**진단이 맞으면 처방도 맞다고 넘어가게 된다.** 남이 제시한 해법을 검토할 때
물어야 할 것은 두 개다.

1. 이 진단이 사실인가 — 막힌 지점이 정말 여기인가
2. 이 처방이 **충분**한가 — 이걸 적용한 뒤 목적이 달성되는가

1번이 명쾌하게 참일수록 2번을 건너뛴다. 이번엔 1번의 근거(빌드 설정 주석에
목적이 적혀 있다)가 워낙 선명해서 더 그랬다.

검증 방법도 갈린다. 1번은 코드를 읽어 답하지만, **2번은 처방을 적용한 상태를
만들어 목적까지 실행해 봐야 답이 나온다.** 여기서는 tarball 을 설치한 소비자에서
번들을 실제로 평가해 보고서야 폰트 구멍이 드러났다.

### 적용 체크리스트

- [ ] 남의 해법을 받았을 때 진단과 처방을 **분리해서** 판정했는가?
- [ ] "이걸 적용하면 원래 하려던 일이 끝나는가" 를 실행으로 확인했는가?
- [ ] 상대가 그 해법에 도달한 지점이 어디인지 물었는가 — 막힌 지점을 아직 못
      지났다면 그 너머는 검증되지 않은 추측이다
- [ ] 처방을 반려하지 않고 **보강**했는가? (진단이 맞으면 처방은 대개 필요조건이다)

## L7. 검증 환경은 심링크로 조립하지 말고 tarball 로 설치한다

**Date**: 2026-09-09
**Source**: 소비자 관점 검증용 임시 디렉터리를 심링크로 만들다 프로젝트
`node_modules/opentype.js` 를 순환 심링크로 덮어써 패키지를 파손

### 문제

스크래치패드에 소비자 디렉터리를 만들면서 의존성을 심링크로 끌어다 썼다.

```sh
ln -sfn <repo>/node_modules "$SP/node_modules"          # 1) 통째로 링크
cd "$SP" && ln -sfn <repo>/node_modules/opentype.js node_modules/opentype.js  # 2)
```

2번의 `node_modules/` 는 1번이 만든 심링크라 **리포의 진짜 `node_modules` 를
가리킨다.** 그래서 이 명령은 리포의 `opentype.js` 패키지 디렉터리를 자기 자신을
가리키는 심링크로 교체했다. 원본 디렉터리는 사라지고 `ERR_MODULE_NOT_FOUND` 가
났다. `pnpm install` 로 복구했다.

### 패턴

**심링크된 디렉터리 안에 링크를 만들면 링크가 아니라 원본을 건드린다.** 격리하려고
만든 장치가 격리를 깨는 경로가 된다.

애초에 목적에 비해 틀린 도구였다. 확인하려던 것은 "npm 으로 설치한 소비자가 이
패키지를 쓸 수 있는가" 인데, 심링크 조립은 `exports` 는 흉내 내도 `files` 필드,
tarball 에 실제로 들어가는 파일, 설치 시 의존성 해석은 흉내 내지 못한다. 실제로
이번에 문제였던 "tarball 에 폰트가 0개" 는 심링크 환경에서는 **드러날 수 없는**
결함이었다 — 리포를 그대로 가리키니 폰트가 항상 거기 있다.

L5 가 "검증 도구가 무엇을 못 보는지 먼저 확인한다" 였는데, 이건 그 도구가 못 보는
정도가 아니라 **검증 대상을 반대로 보증해 주는** 경우다.

### 적용 체크리스트

- [ ] 소비자 관점 검증은 `pnpm pack:tgz` → 별도 디렉터리에 `npm install <tgz>` 로
      하는가? (심링크·`file:` 참조·workspace alias 아님)
- [ ] 스크래치 디렉터리에 `node_modules` 심링크를 걸어 두고 그 **안에** 무언가를
      만들고 있지 않은가?
- [ ] 리포 밖에서 도는 스크립트가 리포 안의 경로에 쓰기를 하는가? 읽기만 해야 한다
- [ ] 실험이 끝난 뒤 `node -e "require.resolve('<pkg>')"` 로 의존성이 멀쩡한지
      확인했는가?

## L8. 테스트가 캡슐화에 막히면 라이브러리가 아니라 테스트를 의심한다

**Date**: 2026-09-09
**Source**: `fizzex/svg` 작업 중 소비자 흉내 테스트가 컴파일에 막히자 `Surface` 를
루트로 공개. 사용자가 "그거 해킹으로 보이는데?" 라고 지적

### 문제

소비자 관점 검증 스크립트를 쓰면서 검증 목적에 없던 `Projector` 조립을 끼워 넣었다.

```ts
declare const surface: import('fizzex').Surface;   // 내가 방금 타이핑한 줄
new Projector(surface, config, myMetrics).render(box);
// → Namespace 'fizzex' has no exported member 'Surface'
```

그리고 **테스트를 고치는 대신 `src/box/index.ts` 에 export 를 추가했다.**

테스트가 실패하면 해석은 둘이다 — 라이브러리에 구멍이 있거나, 테스트가 잘못됐거나.
첫 번째로 단정하고 두 번째를 검토하지 않았다. 나중에 확인해 보니 답은 두 번째였다.

| 확인한 것 | 결과 |
|---|---|
| `Surface` 를 타입으로 쓰는 곳 | 전부 패키지 내부, 전부 `surface.js` 직접 import |
| 배럴(`box/index.ts`)을 경유하는 곳 | **0건** |
| `new Projector` 18곳 | 전부 내부 |
| website(유일한 실사용 소비자) | Projector·Surface **0건** |

밖에서 `Projector` 를 조립한 소비자가 존재한 적이 없다. 그래서 그 인자 타입이
공개인지 아닌지가 문제될 자리 자체가 없었다.

### 패턴

**내가 판 자리를 구멍이라고 불렀다.** 실재하는 요구가 아니라 "소비자라면 이렇게
쓰겠지" 라는 내 가정이 막힌 것인데, 그것을 라이브러리의 결함으로 보고했다.

더 나쁜 것은 그 다음이다. 뚫은 구멍을 내가 쓴 테스트로 통과시키고 "목적 달성
확인" 이라고 보고했다. **통과를 보장한 것은 라이브러리가 옳아서가 아니라 방금
내가 그렇게 만들었기 때문이다.** 검증의 형식만 남고 내용이 없다.

배럴은 패키지 **밖으로** 내보내는 통로다. 내부는 파일을 직접 import 한다. 그러니
"배럴에 없다" 는 결함의 징후가 아니라 **"밖에서 쓸 일이 없었다" 는 설계 기록**이다.

### 적용 체크리스트

- [ ] 테스트가 컴파일에 막혔을 때, 라이브러리를 고치기 전에 **테스트가 틀렸을
      가능성**을 먼저 검토했는가?
- [ ] 그 심볼을 실제로 필요로 하는 소비자가 있는가? 있다면 어디인가? (내가 방금
      쓴 검증 코드는 소비자가 아니다)
- [ ] 검증 코드가 검증 목적에 필요한 범위를 넘지 않았는가? (metrics 주입을
      확인하려는 스크립트에 Projector 조립은 필요 없었다)
- [ ] 공개 표면을 늘린 뒤 그것을 쓰는 테스트로 "검증했다" 고 말하고 있지 않은가?
      — 순환이다
- [ ] 캡슐화를 뒤집기 전에 "누가 이걸 필요로 하는가" 를 먼저 확인했는가?
      순서가 거꾸로면 근거가 결론을 따라간다
